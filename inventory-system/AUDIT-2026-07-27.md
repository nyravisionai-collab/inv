## 🔴 Critical

### 1. Transfer માં બિન-આંકડાકીય quantity આખો સ્ટોક 0 કરી નાખતું હતું

* **ફાઇલ:** `backend/src/controllers/inventoryController.js` — `createTransfer()`
* **મૂળ કારણ:** ગાર્ડ `Number(item.quantity) <= 0` હતો. `Number('abc')` એ `NaN` છે
  અને `NaN <= 0` હંમેશા `false` — એટલે ગાર્ડ પસાર થઈ જતું. પછી
  `adjustWarehouseStock(..., -Math.abs(NaN))` એ `warehouse_stock.quantity` માં
  `NaN` લખતું, અને `updateProductStock()` એનો SUM લઈને `current_stock` **0** કરી દેતું.
* **Reproduce:** 50 એકમ સ્ટોકવાળા product પર
  `POST /api/stock/transfers {items:[{product_id, quantity:'abc'}]}` →
  `201 Created`, અને `GET /api/products/:id` માં `current_stock: 0` (બંને વેરહાઉસ 0).
* **અપેક્ષિત:** 400 ભૂલ, સ્ટોક 50 યથાવત્.
* **ફિક્સ:** દરેક line ને `toNumber(..., {min:0})` થી normalize કરીને validate કરી,
  quantity ≤ 0 નકારી. હવે 400 `ERR_NOT_NUMBER`, સ્ટોક અકબંધ.

### 2. Transfer અસ્તિત્વ ન ધરાવતા વેરહાઉસમાં માલ ગુમાવી દેતું હતું

* **ફાઇલ:** એ જ ફાઇલ, `createTransfer()`
* **મૂળ કારણ:** `from_warehouse_id` / `to_warehouse_id` નું અસ્તિત્વ ક્યાંય ચકાસાતું નહોતું.
  સ્ત્રોતમાંથી માલ ઘટતો પણ ગંતવ્ય તરીકે એક ભૂતિયા `warehouse_stock` row બનતી,
  જે `listWarehouses` (`is_active = 1` join) માં ક્યારેય દેખાતી નહીં — એટલે માલ ગાયબ.
* **Reproduce:** `to_warehouse_id: 999999` સાથે transfer → `201 Created`, માલ અદૃશ્ય.
* **અપેક્ષિત:** 400, કોઈ સ્ટોક હલચલ નહીં.
* **ફિક્સ:** બંને વેરહાઉસ `is_active = 1` સાથે ચકાસાય છે → 400 `ERR_NOT_FOUND`.

## 🟠 High

### 3. Expense/Income/Journal/Transfer/Adjustment નંબર delete પછી અથડાતા હતા

* **ફાઇલ:** `backend/src/services/numberService.js`
* **મૂળ કારણ:** `nextExpenseNumber()` વગેરે `COUNT(*) + 1` વાપરતા હતા, પણ કૉલમ
  `UNIQUE` છે અને rows delete થઈ શકે છે. વચ્ચેની row કાઢ્યા પછી count એવા નંબર પર
  આવે જે હજી વપરાશમાં છે.
* **Reproduce:** 3 expense બનાવો (EXP-00001..3), વચલી કાઢો, ચોથી બનાવો →
  `500 UNIQUE constraint failed: expenses.expense_number`. વપરાશકર્તા માટે ખર્ચ
  નોંધવાનું સંપૂર્ણ બંધ થઈ જાય.
* **અપેક્ષિત:** નવો, ન વપરાયેલો નંબર મળે.
* **ફિક્સ:** સહિયારું `nextSequentialNumber()` — અત્યાર સુધીના સૌથી ઊંચા નંબરથી
  શરૂ કરી, વપરાયેલા નંબર છોડી દે છે. પાંચેય કાઉન્ટર એ વાપરે છે.

### 4. નકારાત્મક / NaN રકમ સ્વીકારાતી હતી (Expense, Income, Payment)

* **ફાઇલો:** `accountingController.js`, `paymentController.js`
* **મૂળ કારણ:** ચેક `if (!category || !amount)` હતો — `-500` truthy છે એટલે પસાર.
  `Number('abc')` → `NaN` → SQLite માં `NULL` → કાચી 500 ભૂલ.
* **Reproduce:** `amount: -500` વાળો expense → `201`, અને bank balance **વધી** જાય
  (ખર્ચ હોવા છતાં). `amount:'abc'` → 500 `NOT NULL constraint failed`.
* **અપેક્ષિત:** 400 validation ભૂલ.
* **ફિક્સ:** `toNumber(..., {min:0})` + `> 0` તપાસ; ValidationError નો status/code
  પસાર થાય એ માટે catch બ્લોક સુધાર્યા.

### 5. Journal entry માં નકારાત્મક રકમ અને ખાલી ખાતાનું નામ

* **ફાઇલ:** `accountingController.js` — `createJournal()`
* **મૂળ કારણ:** માત્ર `|debit - credit| < 0.01` ચકાસાતું. `-100` debit અને `-100`
  credit સંપૂર્ણ સંતુલિત ગણાય. ખાતાનું નામ ક્યાંય required નહોતું.
* **Reproduce:** `lines:[{account_name:'A',debit:-100},{account_name:'B',credit:-100}]`
  → `201`, ખાતાવહીમાં નકારાત્મક entry. ખાલી નામ સાથે પણ `201`.
* **અપેક્ષિત:** બંને કિસ્સામાં 400.
* **ફિક્સ:** પ્રતિ-line ખાતાનું નામ required, debit/credit `min: 0`, અને કુલ > 0.

### 6. Modal નું initial focus header ના close બટન પર જતું હતું

* **ફાઇલ:** `frontend/src/components/Modal.jsx`
* **મૂળ કારણ:** focus selector DOM ક્રમમાં પહેલું focusable તત્વ પસંદ કરતું, જે
  હંમેશા header નું ✕ બટન છે — `autoFocus` વાળું ફીલ્ડ હોવા છતાં.
* **Reproduce:** Category/Brand modal ખોલો (`<input autoFocus>` છે) → focus ✕ પર;
  તરત ટાઇપ કરવાથી કશું લખાય નહીં, અને Enter/Space મોડલ બંધ કરી દે.
* **અપેક્ષિત:** પહેલું ફોર્મ ફીલ્ડ focus થાય.
* **ફિક્સ:** `.modal-body` નાં ફીલ્ડને પ્રાધાન્ય; વળી જો dialog ની અંદર પહેલેથી
  કંઈક focused હોય તો effect એને ખસેડતું નથી (React ના `autoFocus` નું સન્માન,
  અને ટાઇપિંગ વચ્ચે caret ન ખેંચાય એની ખાતરી).

  > નોંધ: આ selector લખતી વખતે `'.modal-body ' + FOCUSABLE` એ ખોટું છે — CSS
  > selector list માં prefix માત્ર પહેલા entry ને લાગુ પડે છે. મારો પહેલો પ્રયાસ
  > આ જ કારણે ટેસ્ટમાં નિષ્ફળ ગયો; હવે દરેક ભાગ પર અલગ prefix લગાવાય છે.

### 7. Body scroll બહુવિધ modal માં વહેલો unlock થઈ જતો હતો

* **અપેક્ષિત:** દરેક input પોતાની row સાથે જ જોડાયેલું રહે.

### 9. State ને સીધું mutate કરવું (Sales, Journals, Transfer, Adjustment)

* **મૂળ કારણ:** `const n = [...items]; n[idx].field = v; setItems(n)` — છીછરી નકલ
  છે, એટલે `n[idx]` એ *એ જ* object છે જે state માં છે. Sales ના `addItem()` માં
  `next[exists].quantity += 1` પણ એ જ રીતે mutate કરતું.
* **અસર:** React ને જૂનું અને નવું object સરખું લાગે; StrictMode/concurrent
  રેન્ડરિંગમાં અપડેટ છોડાઈ શકે અને ટાઇપ કરેલો ડેટા ખોવાય.
* **ફિક્સ:** બધે functional `setState` + પ્રતિ-row નકલ (`{...row, ...patch}`).

### 10. Modal બંધ કરવા માટે overlay નો ઉપયોગ ડ્રેગ પર પણ થતો

* **ફાઇલ:** `Modal.jsx`
* **મૂળ કારણ:** `onMouseDown={onClose}` overlay પર હતું અને અંદરના div પર
  `stopPropagation`. પણ overlay ના પોતાના child (dialog) ની બહાર શરૂ થતું કોઈ પણ
  press બંધ કરી દેતું. હવે સ્પષ્ટ `e.target === e.currentTarget` તપાસ છે, અને
  onClose ref માંથી લેવાય છે (તાજું handler).

* **`AuthContext`:** `t`, `formatMoney`, `toggleTheme` બધા memoized — એટલે એના
  પર આધારિત child effects બિનજરૂરી રીતે ચાલતા નથી.
* **`ToastContext`:** `toast` સ્થિર છે; timeout પ્રતિ-toast છે.
* **કોઈ પણ component બીજા component ની અંદર define થયેલું નથી** — એ સૌથી સામાન્ય
  "દરેક કીસ્ટ્રોકે input remount થાય" કારણ અહીં હાજર નથી.
* **Sale/Purchase cancel:** સ્ટોક બરાબર reverse થાય છે (લાઇવ ચકાસ્યું), બે વાર
  cancel કરવાનું અટકાવાય છે, અને transaction માં લપેટાયેલું છે.
* **`nextNumber()` (invoice/bill/payment):** પહેલેથી atomic UPDATE + collision
  guard વાપરે છે. બરાબર છે.
* **Gujarati ટાઇપિંગ:** કોઈ input પર `pattern`/`maxLength`/ટ્રાન્સફોર્મ નથી;
  ગુજરાતી ટેક્સ્ટનો ટેસ્ટ ઉમેર્યો, પસાર.
